# ADR-021：経路の照合は、アプリが同じ処理に振り分けうる綴りをすべて保護する

日付：2026-09-30

## 決定

Gate の経路の照合（`routes[].match`）は、アプリが同じハンドラに振り分けうる綴りを、すべてその経路として扱う。

- **大文字小文字を区別しない。**
- **末尾のスラッシュ。** 付いていてもいなくても同じ経路とする。
- **`/**` で終わる経路の基底。** `/checkout/**` は `/checkout` 自身も含む。
- **候補の綴り。** リクエストのパスから次の候補を作り（`routeCandidates`）、各候補で最初に一致した経路を取り、圧の最も高いものを採る。
  - パスそのもの
  - 次の正規化をすべて施したもの
    - `%XX` を 1 回だけ復号する（`%2F` も含む）
    - `\` を `/` とみなす
    - `;params` を落とす
    - 連続するスラッシュをまとめる
    - ドットのセグメントを解決する
    - 末尾のスラッシュを落とす
  - 上の正規化に加えて、最後のセグメントの拡張子（`.json` など）か末尾のドットを落としたもの
- **絶対形式の要求対象。** `GET http://host/checkout HTTP/1.1` は、そのパスで照合する。Node アダプタは `originForm()` を使う。Host の後ろに URL をつないだ形にはしない。

## 理由

- **実際のアプリで素通りできた。** 本物の Express 5.2.1 で確かめたところ、署名のない自動化（`python-requests`）が P2 の重要経路のハンドラに届いた綴りが 7 つあった。
  - `/CHECKOUT/1`、`/Checkout/1`、`/LOGIN`
  - `/login/`、`/Login/`
  - `http://shop.example/checkout/1`（authority が別でも同じ）
  - `POST /checkout` 自身。spec §11.4 の例 `/checkout/**` が、決済の送信先そのものを守っていなかった。
- **誤判定の側は人間に及ばない。** 保護しすぎた場合に影響を受けるのは、未検証の自動化だけだ。`decide()` は UNKNOWN（人間を含む）に決して作用しない（spec §10.8「人間の体験を変えない」）。
- **守れなかった場合の損失は大きい。** 決済・ログインの経路を素通りされる。
- **正規化の根拠。**
  - プロキシ：nginx の `merge_slashes`
  - サーブレットコンテナ：`;jsessionid`
  - IIS：`\` と末尾のドット
  - Rails や Django REST：形式の接尾辞
  
  どれも実在のフレームワークや前段が、同じハンドラへ振り分ける綴りだ。
- **最高の圧を採る。** 最初の一致ではなく最高の圧を採るのは、低い圧の経路へ綴りで逃げられないようにするためだ。例：サイトの既定が 3 のとき、`/%70ublic/x` は `/public/**`（圧 0）に落ちない。
- **明示した経路はそのまま効く。** 正しい綴りで明示した低圧の経路（例：`/checkout/help` を 0）は、そのまま効く。

## 捨てた代替案

- **アプリのルーターに照合を任せる。** Gate はアプリの前で判定するので、ルーターの結果を待てない。フレームワークごとにアダプタが違う。
- **正規化後の 1 つの綴りだけで照合する。** 元の綴りでしか一致しない設定（大文字を含む match など）が壊れる。
- **大文字小文字を区別する設定を残す。** 区別するフレームワークもある。ただし、区別しない照合で困るのは未検証の自動化だけなので、既定は保護の側に倒した。

## 見直す条件

- **他のフレームワークの規則。** Next.js、Hono、Fastify、Workers などで、この候補の外にある綴りを同じハンドラへ振り分けるものが見つかったとき。コーパスに足し、候補を増やす。
- **サイトの宣言。** サイトが「このアプリは大文字小文字を区別する」と宣言したい要望が出たとき。
- **ヘッダーによる振り分け。** `X-Original-URL` / `X-Rewrite-URL` で振り分けるアプリ（古い Symfony、IIS の URL Rewrite）に出会ったとき。今は候補に入れていない。
