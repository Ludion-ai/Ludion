# ADR-020：fail_mode が効くのは Gate 自身の故障だけ。鍵の発見の失敗は UNVERIFIED

日付：2026-09-30

## 決定

1. **fail_mode が効くのは、Gate 自身の故障だけ。** 対象は次のとおり。
   - 時計の異常（例外、NaN）
   - Gate 内部の検証が時間切れになること
   - Registry 鍵が使えないために、経路が求める立場（Depth、Ballast）を確かめられないこと
   - Gate のコードの予期しない例外
2. **鍵の発見で起きたことは、何であれ UNVERIFIED。** fail_mode は見ない。含まれるもの：
   - ディレクトリの 404
   - ネットワークの失敗
   - 応答が遅いこと
   - resolver 自身の例外や、壊れた返り値
   - 発見の予算切れ
   
   spec §10.8 の「dir is unavailable → UNVERIFIED」そのまま。Pressure 2 以上では拒否される。
3. **Pressure 0〜1 は常に開く。** `failMode: { pressure_0_1: "closed" }` は起動時に TypeError で拒否する。文字列の `failMode: "closed"` / `"open"` は Pressure 2〜3 だけに効く（以前は "closed" が P1 にも効き、故障時に人間にまで摩擦がかかりえた）。
4. **時間の予算は `timeoutMs`**（既定 3000ms）。1 リクエストに Gate が足してよい時間の上限。
   - 鍵の発見は、その少し手前で打ち切る：`timeoutMs − min(250, timeoutMs/5)`。
   - 打ち切った取得は裏で続け、キャッシュを埋める（§11.6「鍵集合の取得は非同期」）。
   - resolver の取得は、fetch の実装が abort を無視しても自分の期限で必ず終わる。
5. **sink は待たない。** 投げても、reject しても、永遠に返らなくても、リクエストには 0ms。
6. **受領証の署名が失敗しても、判定は変えない。** 受領証は証拠であって判定ではない。
7. **Registry 鍵が読めなくても Gate は起動する。** 壊れた鍵は 1 本ずつ飛ばし、状態は `gate.health` に出す。

## 理由

- **発見の失敗で開けてはいけない。** Signature-Agent の URL を選ぶのはリクエストする側だ。発見の失敗が fail_mode "open" で開くなら、攻撃者は応答の遅いサーバ（tarpit）を指すだけで Pressure 2 を素通りできる。GATE-5 の「no tarpit bypass」テストがこれを固定している。
- **Gate の故障は開けてよい。** 時計や Registry 鍵の状態、Gate 内部の不具合は、リクエストの中身では引き起こせない。だからサイトが選んだ fail_mode に従ってよい。
- **署名の処理中の例外は SPOOFED のまま。** 不正な構造化フィールドや壊れた Staple など、攻撃者が触れる入力の処理で起きた例外は、今までどおり SPOOFED（拒否側）にする。これも同じ理由で、故障扱いにしない。

## 捨てた代替案

- **resolver の失敗をすべて Gate の故障として fail_mode に従わせる。** 上の tarpit 攻撃が通る。
- **Pressure 0〜1 でも "closed" を許す。** 故障時に人間に摩擦がかかる。「人間の体験を変えない」（§10.8）に反する。
- **sink を待ったうえでタイムアウトを付ける。** 待つ理由がない。メタデータは判定に使わない。

## 見直す条件

- **エラーコード。** fail_mode "closed" の拒否は、今は `signature_required`（401）で返している。署名した正規のエージェントには紛らわしい。Gate の障害を示す専用のコード（例：503 `gate_unavailable`）を §10.11 に足すかは、未決。
- **初回取得中の Pressure 0〜1。** §11.6 のとおり、最初の鍵の取得を待たずに通す実装に変える。変えるなら、SEED-2 と GATE-4 と一緒に見直す。
