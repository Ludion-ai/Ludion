# 登録フォームの受け口は、サイトと同じ Worker に置く

日付：2026-10-01（夜勤 7、WEB-8）

## 決定

1. 受け口は Web 標準の関数にする：`handleSignup(Request) → Response`（`site/edge/signup.mjs`、依存なし）。
   - プレビューでは、サイトの静的ファイルを配る Worker（`site/edge/worker.mjs`）が動かす。静的ファイルに当たらないリクエストだけが Worker に来る。
   - Vercel では薄いアダプタ（`site/api/signup.js`）が同じ関数を呼ぶ。Node の Fetch API でも動く（`site/test/signup.test.mjs`）。
   - クライアントの見分けは、実行環境が決めたヘッダーだけで行う。Workers は `CF-Connecting-IP`、Vercel は `X-Real-IP`。クライアントが選べるヘッダー（`X-Forwarded-For`）は読まない。
2. 置き場所は同じオリジンの `/api/signup`。フォームはトップ（`/` と `/ja`）に置く。
   - WEB-5 と WEB-6 の許可リストはサイト自身のオリジンだけ。送信先もその中に置く。
   - scan のページ（`/scan`、`/ja/scan`）には置かない。scan のページからは何も送らない（WEB-6）。
   - 本文は 4 KiB まで。scan のページの「このサイトには、ログを受け取る口がありません」は、この受け口ができても真のまま。
3. ボットの落とし方は2つ。
   - ハニーポット：`message` という名の欄を `display: none` の中に置く。人には見えず、フォーカスも自動入力も届かない。すべての欄を埋めるボットはここも埋める。埋まっていたら、人と同じ応答（`200 {"ok":true}`）を返して捨てる。ボットには違いが分からない。
   - レート制限：クライアントごとに 10 分で 5 回、全体で 10 分で 100 回（`LIMITS`）。超えたら `429` と `Retry-After`。
     - すべての POST を数える。壊れた本文もハニーポットも数える。
     - 止められている間の試行も数える。連打し続けるクライアントは止まったまま。
     - 1つのクライアントが自分の上限で止められている間は、全体の枠を埋めない。1台の連打で全員が止まることはない。
     - 覚えるクライアントは 1 万まで。超えたら最も長く来ていないものを忘れる。
4. 通知は `SIGNUP_WEBHOOK_URL`（Slack か Discord の incoming webhook）。
   - 通知先が 2xx を返したときだけ「受け付けました」と答える。無ければ 503、失敗か 5 秒の時間切れなら 502。フォームは「送信できませんでした」と言う。受け取ったふりはしない。
   - 通知の文面は Slack のマークアップ（`&`、`<`、`>`）をエスケープし、Discord には誰にも通知させない（`allowed_mentions`）。メールアドレスは `<`、`>`、空白を含めない形だけ通す。
   - ログには何も書かない。メールアドレスは通知の中にだけある。
5. フォームには `action` を付けず、送信ボタンはスクリプトが動くまで押せない。
   - `<form action="/api/signup">` は WEB-5 のリンクの規則（出荷したファイルに解決すること）に掛かる。規則を緩めない。
   - JS のない POST を受けて返す画面も作らない。サイトの検索と scan も JS が要る。
6. フォームと受け口は、欄の名前、ハニーポット、立場の一覧を `site/edge/form.mjs` から共に読む。
7. `site/edge` は別の npm プロジェクトにする（wrangler 4.144.0。参照アプリの Workers と同じ版）。サイトの `npm ci` に workerd を足さない。

## WEB-8 の測り方

- プレビューはまだ出せない（WEB-1 はトークン待ち）。だから、プレビューに出す成果物そのものを手元で動かす。
  - 本物の `site/edge/wrangler.json` の assets を、ビルドした dist に向ける。
  - `wrangler dev`（workerd）で Worker を立て、通知先はローカルの webhook のスタブにする。
- 人（+）：`/` と `/ja` で、Chromium がフォームを埋めて送る。
  - ページが送るのは、自分のオリジンの `/api/signup` への POST の1本だけ。
  - 通知には、その人の欄がそのまま1件だけ届く。
  - そのあとでだけ、ページが「受け付けました」と言う。
- ボット（−）：
  - ブラウザで全部の欄を埋めて送る。直接 POST する（JSON とフォーム形式）。どちらも人と同じ応答で、通知には届かない。
  - 1つのクライアントから 10 件。5 件が通り、残りは 429 で、通知に届かない。別のクライアントは通る。止められたクライアントのページは、そのことを英日で言う。
- 検査が噛むこと：受け口に4つの故障を仕込む。どれも狙いの規則で捕まる。
  - ハニーポットを無視する。
  - 制限しない。
  - 制限の鍵が空（全員で1つの枠）。
  - 通知せずに ok と答える。
- プレビューが出たら、同じ `exercise` をプレビューの URL に向ける。そのためには、通知先を観測できる形（プレビュー用の webhook）が要る。

## 捨てた候補

- **Pages Functions**：プレビューは Workers の静的アセットにした（docs/DEPLOY.md 2）。Pages は旧 Ludion の資源と名前や結びつきが重なる恐れがある（NIGHT.md §7）。
- **Vercel だけ**：DNS は Cloudflare にあり、プレビューは `*.workers.dev`。Vercel はアダプタで残した。
- **全体で一貫した制限（Durable Objects、KV、Workers の Rate Limiting バインディング）**：アカウントの設定と、場合によってはお金の判断が要る。手元で同じ形に測りにくい。
  - v0 はメモリ内で、インスタンス（isolate）ごとに数える。止めるのは連打で、分散した総当たりはハニーポットに任せる。
  - 要るようになったら、`createLimiter` を差し替える。形は `take(client) → 待つ秒数` だけ。
- **Turnstile や reCAPTCHA**：第三者への通信になる。WEB-5 の許可リストは自分のオリジンだけ（NIGHT.md §2）。
- **時間のわな（表示から送信までが速すぎたら落とす）**：今回は入れない。ハニーポットと制限で合格条件を満たす。偽の陽性（自動入力の速い人）を測る手段がまだない。
- **wrangler をサイトの devDependencies に入れる**：WEB-2〜6 のたびに workerd を入れることになる。

## 未決

- 制限はインスタンスごと。Cloudflare の複数の拠点や isolate に散った連打は、それぞれの枠で数えられる。
- 本番の文面「入力された内容は Ludion のチームに届き、Ludion についてのご連絡に使います」は、個人情報の利用目的の表示にあたる。会社としての約束なので、本番の前に人間が読む（STATE.md の人間待ち）。プライバシーポリシーはまだない（spec §21）。
- `SIGNUP_WEBHOOK_URL` はまだない（人間待ち）。それまで、デプロイしたフォームは「送信できませんでした」と答える。
