# ドラフトの版は1か所に留め、datatracker とリポジトリの両方に当てる（STD-4）

日付：2026-10-01

## 決定

- 実装しているドラフトとその版を `accept/std4/pins.json` の1か所に書く。
  - `draft-ietf-webbotauth-httpsig-protocol` -00
  - `draft-meunier-webbotauth-registry` -03
- STD-4（`accept/std4/run.mjs`）は2つを確かめる。
  - **datatracker**：`/doc/<name>/doc.json` を読む。
    - 留めた版が最新なら通る。
    - 新しい版が出ていれば、最初の新しい版の公開から 7 日間は通る。そのあいだ、出力に issue の文面を載せる（何が変わったか、iddiff のリンク、期限）。7 日を過ぎたら落ちる。
    - 状態が `Replaced` なら、`relateddocument`（replaces）で後継をたどる（最大 5 段）。時計は置き換えの時点から進む。
    - 留めた版が datatracker より先なら落ちる。
  - **リポジトリ**：追跡しているテキストファイルにある Web Bot Auth のドラフトの参照（`draft-…webbotauth…-NN`、`draft-…web-bot-auth…-NN`）は、すべて留めたドラフトの留めた版でなければならない。留めていない Web Bot Auth のドラフトを版つきで書いても落ちる。
    - ADR、STATE.md、outbox は、その日の記録なので読まない。
- datatracker を読めないときは落ちる（3 回まで試す）。分からないことを PASS にはしない。
- 検査器そのものの失敗の道は、`accept/std4/drafts.test.mjs` がオフラインで確かめる（`npm test` に入れた）。
  - 偽の datatracker を使う。
  - 仕込んだ 6 つの故障をすべて捕まえた：猶予が終わらない、置き換えをたどらない、違う版を受け入れる、読めないのに通す、留めていないドラフトを受け入れる、先走った版を受け入れる。

## 理由

- 版の食い違いは、コードより先に文書で起きる。spec、MISSION、コードのコメントが別々の版を名乗り始めたら、どれに合わせて実装したのか誰にも分からなくなる。1 か所に留めて、全部をそれに当てれば、版を上げるときに直す場所を検査器が並べてくれる。
- 7 日の猶予は MISSION.md の定義どおり。新しい版が出た日に、関係のない PR まで止めない。

## 捨てた代替案

- **issue を自動で立てる。** 公開リポジトリへの書き込みは、人間の承認が要る外向きの行為として扱う。今は文面を出力に載せるだけにした。自動化するかは人間待ちに書いた。
- **datatracker が落ちているときは PASS にする。** 「分からない」を合格にすると、ラチェットの意味がなくなる。一時的な失敗は、CI の再実行で済む。
- **scoreboard を変えて、レベル 2 を定期実行だけにする。** scoreboard と CI は元のレーンが持っている（NIGHT.md §1）。この検査は 1 秒かからない。

## 見直す条件

- datatracker の不調で CI が何度も止まるなら、スケジュール実行へ移す。これは scoreboard の変更になるので、元のレーンと一緒に決める。
- web-bot-auth（npm）の版と、ドラフトの版の対応は見ていない。ライブラリが新しい版を実装したら、両方を一緒に上げる。
